# Inventory: industry, mining, reprocessing and planets (EvEJS)

Four sibling service trees under `$EVEJS_RUN/server/src/services/`: `industry/` (22 JS files, 12,090 LOC), `mining/` (23 JS files, 14,432 LOC plus a 34,386-line synthetic ice JSON), `reprocessing/` (9 files, 3,957 LOC) and `planet/` (10 files, 11,586 LOC) — about 42,000 LOC of game logic. None of it is self-contained: all four lean on a fifth tree, `services/inventory/` (`itemStore.js` 8,088 LOC + `itemCustody.js` 2,725 LOC + 15 small `*ItemCustody.js` adapters), which is the single writer of the `items` table and the thing that actually makes "material in, product out" survive a crash. There are **zero test files in the entire release** (`find` for `*.test.js`/`*.spec.js`/`test/` over the repo returns nothing), so every status below is read off the code path, not off a passing test. The spread of maturity is wide: reprocessing and planetary industry read as genuinely complete; manufacturing is complete for manufacturing only; the system cost index is an admitted one-line stub (`industrySystemCostIndex.js:34`); and mining's ore/ice/gas *field* content is substantially invented or scraped rather than derived from the client.

## The item custody model

There is one writer of the `items` table and one command boundary in front of it.

**The two layers.** `services/inventory/itemStore.js` owns the table (`itemStore.js:12-18`: "itemStore owns the items table (sole writer); access flows through a strict ownership-scoped repository"). `services/inventory/itemCustody.js` is a *command boundary* in front of it — a synchronous `transfer(command)` that takes detached data only, so that "the executor can later be replaced by an authority RPC" (`itemCustody.js:9-17`). Every domain that needs to move goods it does not own gets a thin adapter: `industryInstallItemCustody.js` (183 lines), `reprocessingItemCustody.js` (196), `planetaryCustomsItemCustody.js` (210), `marketItemCustody.js` (307), and 11 more. The adapters contain no logic — `industryInstallItemCustody.js:33-59 move()` just names a reason and calls `itemCustody.transfer`.

**What identifies a location.** A location is the triple **`(ownerID, locationID, flagID)`**, and nothing else. `itemCustody.js:44-59` defines 14 `CUSTODY_REF_KIND` values (`OWNER_LOCATION`, `STATION_HANGAR`, `SHIP_BAY`, `FITTING_SLOT`, `IN_SPACE`, `CONTAINER`, `DELIVERIES`, `CORPORATION_OFFICE`, `MARKET_ESCROW`, `CONTRACT_ESCROW`, `ASSET_SAFETY_WRAP`, `REDEEM_TOKEN`, `NATIVE_WRECK`, `VOID`), but `itemCustody.js:390-481 custodyRef` shows every one of them collapsing to that same triple — `stationHangar(ownerID, stationID)` is literally `{ownerID, locationID: stationID, flagID: 4}`. The `kind` is a *routing/validation* tag, not a different address space. Even the virtual ones are forced into the triple: `custodyRef.contractEscrow(contractID)` at `:456-468` synthesises `locationID = 9_300_000_000 + contractID` with `ownerID: 1`.

`flagID` is EVE's real `flagID` enum, hardcoded at `itemStore.js:98-144`: `HANGAR: 4`, `CARGO_HOLD: 5`, `DRONE_BAY: 87`, `SHIP_HANGAR: 90`, `GENERAL_MINING_HOLD: 134`, `SPECIALIZED_ICE_HOLD: 181`, `SPECIALIZED_ASTEROID_HOLD: 182`, `COLONY_RESOURCES_HOLD: 185`, etc. Fitted modules are not a separate table — they are items whose `flagID` falls in a slot range, `itemStore.js:60-69 FITTING_FLAG_RANGES = [[11,34],[92,99],[125,132],[164,171]]`.

**Escrow is a synthetic locationID range, hand-partitioned.** This is the single most portable idea in the tree, and the one most likely to bite. Each domain carves out a billion-wide band and derives a *per-operation* location inside it:

| band | owner | evidence |
|---|---|---|
| 9_200_000_000 | market escrow | `inventory/marketItemCustody.js:7` |
| 9_300_000_000 | contract escrow | `inventory/contractItemCustody.js:7`, duplicated at `itemCustody.js:35` |
| 9_400_000_000 | reprocessing | `reprocessing/reprocessingSettlementState.js:43` |
| 9_500_000_000 | mission rewards | `agent/missionRewardSettlementState.js:49` |
| 9_600_000_000 | planetary customs | `planet/planetaryCustomsSettlementState.js:37` |
| 9_700_000_000 | industry install | `industry/industryInstallSettlementState.js:39` |
| 9_800_000_000 | jump bridge fuel | `structure/structureJumpBridgeMgrService.js:92` |
| 10_200_000_000 | market seed fill | `inventory/marketItemCustody.js:13` |

Industry derives two escrow locations per operation — `industryInstallSettlementState.js:337-338`: `materialEscrowLocationID = 9_700_000_000 + operationSequence*2`, blueprint escrow is that `+1`. Separately, an *installed* blueprint lives at the fixed sentinel `locationID = 2003` (`industryConstants.js:90 INDUSTRY_INSTALLED_LOCATION_ID = 2003`), which `industryRuntimeState.js:690,708,728,813,1668,1738,1871,3711,3730` tests against all over the place. So "in a job" is not a flag — it is a magic location.

**How ownership transfer is made atomic.** It is not a database transaction. There is no `BEGIN`/`COMMIT` anywhere in `itemStore.js`. The mechanism is three parts:

1. **A durable idempotency receipt ledger, stored inside the items table itself** under the magic key `__evejsInventoryGrantReceipts` (`itemStore.js:86`), read via `getIdempotentGrantReceiptLedger` (`:5461`) and written via `stageIdempotentGrantReceiptLedger` (`:5479`), which *copies the ledger and reassigns it* because the row-overlay mutation plan is shallow and cannot roll back an in-place edit inside a row it handed out (`:5474-5478`).
2. **A whole-table sync fence.** `flushInventoryMoveBatch` (`:328`) calls `repo.flushTableSync("items")` at `:332`. A "transaction" is an `inventoryMoveBatch` token (`:351 createInventoryMoveBatch`) that several moves enlist in (`:298 enlistInventoryMoveBatch`); each returns `durable: false, pending: true` until the batch's single `commit()` flushes the whole table. Only `move-item-to-location` and `transfer-item-to-owner-location` may join a batch (`:5572-5576`) — a *grant* that retires a source row in another table keeps its own fence.
3. **A compensating saga on top**, per domain, for anything that spans tables (items + wallet). `industryInstallSettlementState.js` is the reference: prepare -> move materials and blueprint into the per-operation escrow -> debit wallet -> commit (destroy escrow contents) -> create job; with `compensateRejectedSettlement` (`:558`) to walk it back, a `durableScheduler` (`:965`) to resume after a crash, and `reconcileDurableIndustryInstallSettlements` (`:1030`) at boot. The shared half lives in `_shared/settlementCustodyRecovery.js:5-18`, whose header states the shape plainly: "Every saga (reprocessing, mission rewards, industry installs, planetary customs) runs the same shape: move goods into a per-operation escrow location, then out again, checkpointing each leg into its own durable record."

**How they avoid double-spend.** Four distinct mechanisms, and it is worth noting they do not trust any one of them:

- **Receipt-key fingerprint match.** Before executing, `executeIdempotentInventoryMutation` (`itemStore.js:5568`) looks up the receipt and compares `receiptKey`, `operation` *and* a deep-equal `fingerprint`; a mismatch returns `IDEMPOTENCY_RECEIPT_MISMATCH` with `ambiguous: true` (`:5604-5616`) rather than executing. A replay returns the stored `resultData` with `changes: []` and `committedChanges` populated, so the client is told what happened without the rows moving twice (`:5628-5640`).
- **Operation-identity keys, not state-derived keys.** `invBroker/ownerTransferIdempotencyKey.js:11-23` is a 38-line file that is almost all comment explaining why: a state-derived key would make "dragging an item into a corp hangar and back" replay the first hand-off's receipt — "success reported, nothing moved" — so the key is `<reason>:<random boot id>:<counter>`.
- **A reservation written onto the source row** before the destination is created, for cross-table routes. `itemCustody.js:2080 writeReservedSource` stamps a `custodyReservation` onto the NPC wreck record and fences it; `:2055 reservationMatchesCommand` checks 11 fields before trusting it; `:2106 compensateReservation` strips it on rollback and refuses with `ITEM_CUSTODY_SOURCE_RESERVATION_CHANGED` if it changed underneath.
- **A reentrancy guard.** `itemCustody.js:2585-2589`: a `transfer` while another `transfer` is active returns `ITEM_CUSTODY_REENTRANT_COMMAND`. Single-threaded Node, so this catches re-entry via a synchronous hook, not concurrency.
- **An explicit "I don't know" state.** `itemStore.js:264-267`: a flush failure leaves the in-memory snapshot ahead of SQLite, so the receipt goes into `uncertainIdempotentGrantReceipts` and is "never treated as proof until the corresponding persistence boundary is reconciled". Results carry `ambiguous: true`. This is the most important honest detail in the whole tree.
- **A sequence watermark at boot.** `_shared/settlementSequenceWatermark.js:1-41` raises each settlement's `nextOperationID` above every sequence its wallet receipts already use, because the settlement table and the wallet receipt table have no shared lifetime; a rewind of one would make a new operation "inherit an unrelated operation's committed result" — "reported as success, so the settlement records the charge as applied and completes the job — free".

**Not everything goes through custody.** Mining mints ore with `grantItemsToCharacterLocation` directly (`miningRuntime.js:992`); compression calls `miningIndustry.compressInventoryItem` directly (`inSpaceCompressionMgrService.js:62`); the industry chat commands mint blueprints directly (`industryChatCommands.js:22`). The rule in practice is: **custody is for moving goods that already exist across an ownership or escrow boundary; a mint from nothing skips it.** That is defensible for ore (nothing is lost if the grant fails) but it is why mining's grant-then-decrement order at `miningRuntime.js:992` -> `:1018` is a genuine duplication window.

**What we would have to add to a store that is id/type/owner.** Our `Item` (`$REPO/server/crates/eve-server/src/item.rs:361-373`) already carries `location_id` and `flag_id` — correcting the brief: the *columns* exist, because the client's item row needs them, and `used_volume` (`item.rs:473`) already keys on `(location_id, flag_id)`. What is missing is every **operation**: `Store` has only `insert` (`:490`) and `spawn` (`:499`), plus read-only `items`/`owned_by`/`used_volume`. There is no move, no owner transfer, no split, no merge, no consume. So the work is:

1. **An index on `(owner_id, location_id, flag_id)`.** Today `Store` is a `Vec<Item>` scanned linearly. Industry's `selectExactIndustryMaterialInputs` and reprocessing's input selection both need "all stacks of type T in this hangar", per job.
2. **Stack split and merge as first-class operations**, with the singleton rule already encoded in `spawn` (`item.rs:396-402`, `:533-535`). Reprocessing's own comment at `station/reprocessingService.js:56-58` notes that splitting an oversized stack "creates a NEW item" the client was never told about — so split must emit an item-change notification, not just mutate.
3. **A capacity check on arrival, not on spawn.** `used_volume` exists but nothing calls it as a precondition. Mining stops a cycle with `stopReason: "cargo"` (`miningRuntime.js:1007`) on exactly this.
4. **A reserved synthetic location range for escrow, allocated centrally.** Do *not* copy their eight hand-partitioned bands — pick one range and one allocator. Their own `INDUSTRY_INSTALLED_LOCATION_ID = 2003` sentinel is a second, incompatible convention in the same codebase; we should have one.
5. **An atomic multi-item operation.** Even without durability, industry install must move N material stacks + 1 blueprint + debit a wallet or move nothing. The minimum shape is a *staged mutation plan* — collect the row edits, validate all of them, then apply — which is exactly what their `rollbackPreviousData` (`itemStore.js:385-392`) and `committedChanges` give them, retrofitted. In Rust we can have this for free and cheaply (clone the affected rows, or build an edit list and apply on success), and we should, before any lane writes a job pipeline.
6. **Durable idempotency, only if we persist.** We have a wallet with a journal, so we already have the "money moved" half. If item moves are snapshotted the same way, a receipt keyed by an operation identity (their `ownerTransferIdempotencyKey` reasoning at `invBroker/ownerTransferIdempotencyKey.js:11-23` is correct and worth copying verbatim as a comment) is the cheap insurance. If we do **not** persist items across restarts yet, skip the receipt ledger entirely — storing receipts inside the items blob the way they do (`itemStore.js:86`) is an unbounded-growth wart we should not inherit.
7. **An item-change notification channel.** Every custody result carries `changes` which the caller feeds to `syncInventoryItemForSession` / `emitItemsChangedForSession` (`miningRuntime.js:35-38`). Our store returning only ids means the caller cannot tell the client what changed. **This is the shared seam** — it should land in the store API, not in four lanes separately.

## Dependency order

Edges in, from outside the area first:

1. **Item store with move/transfer semantics -> everything.** Industry install, reprocessing, compression, PI import/export and mining-into-cargo all end in an item row changing location, owner, or quantity. Nothing in this area can be built on a store that only spawns. This is the gate. Our store today (`item.rs:490-556`) cannot do any of it.
2. **Item-change notification -> everything.** Each of the above must tell the client what moved. Their every path goes through `syncInventoryItemForSession`/`emitItemsChangedForSession` (`miningRuntime.js:35-38`). Build this *into* the store seam; four lanes inventing it four ways is the worst outcome.
3. **Docked session + station/structure identity -> industry, reprocessing.** Both need "where am I and may I use this facility". `industryChatCommands.js:9-11` imports `getDockedLocationID`/`isDockedSession` from `structure/structureLocation`; `reprocessingRuntime.js:355 resolveReprocessingContext(session)`. `docs/archive/plan-docked-subsystems.md` is the right home for this edge.
4. **Skills -> industry, reprocessing, mining.** `industryRestrictions.js:18-20` reads `getCachedCharacterSkillMap`; `reprocessingRuntime.js:234-334` is entirely skill multipliers; `miningRuntime.js:39-41`. Without skills, every yield and time is a base-case approximation — which is survivable for a first cut, but means numbers will not match the client's own preview.
5. **Dogma / fitted modules -> mining (hard), industry (soft).** `miningRuntime.js:52-59` pulls `getFittedModuleItems`, `getLoadedChargeByFlag`, `isModuleOnline`, `buildShipResourceState` from `fitting/liveFittingState`; `miningDogma.js` imports `space/combat/weaponDogma`. A mining laser is a module with a cycle, a range, and a crystal. **No fitting, no mining.**
6. **Destiny / space simulation -> mining (hard).** `miningRuntime.js:30-33` imports `space/destiny/identity/interactionScope` (`canEntitiesInteractLocally`); `miningRuntimeState.js` imports `space/destiny/commands/mining.js` and `space/asteroids`; `miningResourceSiteService.js:16` needs `space/worldData`. Asteroids are entities in a scene with positions, and mining is a ranged module cycle against one. **Mining cannot be done docked.** This is the single biggest cost difference between mining and industry.
7. **Wallet with journal -> industry, reprocessing, PI.** `industryInstallSettlementState.js:11-18` imports `adjustCharacterBalanceAsync` and the corp-wallet equivalent; `planetCostCalculator.js:18-22` defines PI journal entry types 96/97/98. **We already have this** — it is the one prerequisite that is done.
8. **Market pricing -> industry (soft), reprocessing (soft).** `industryPricing.js:16-18` needs adjusted average prices for the job install fee; reprocessing needs them for the station's ISK-value tax (`reprocessingRuntime.js:699`). Both degrade cleanly to `basePrice` (`industryPricing.js:45-47`), so this is a *soft* edge: build industry first, refine pricing later.
9. **Structures (Upwell) -> industry facilities, reprocessing rigs, compression, skyhooks.** `industryStaticData.js:11-26` imports five modules from `services/structure/`; `reprocessingRuntime.js:436-498` resolves structure profiles and rig bonuses; `structureCompressionMgrService` is structure-only; `skyhookOfficeReplacement.js` is structure-adjacent. **Without structures, industry and reprocessing work only at NPC stations** — which is a perfectly good first milestone, and the one to aim for.
10. **Starbases (POS) -> POS industry arrays, moon mining.** `industryStaticData.js:14` imports `starbaseIndustryRuntime`; `posMgrService.js` is all POS. Defer entirely.

Edges inside the area:

11. **Reprocessing static data -> mining.** `miningStaticData.js:14` re-exports *everything* from `../reprocessing` — `getTypeMaterials`, `getCompressedTypeID`, `getCompressionSourceTypeIDs`, `isCompressibleType`. Mining's compression is reprocessing's compressed-type map wearing a different hat. **Build reprocessing's static layer before mining's compression.**
12. **Mining -> reprocessing (gameplay).** Ore is only interesting if it refines. But the *code* dependency is the other way round (11), so reprocessing is the earlier build.
13. **Reprocessing -> industry (gameplay).** Minerals feed manufacturing. Again no code dependency; industry reads `industryBlueprints` and consumes whatever is in the hangar.
14. **Industry jobs -> escrow saga -> item store.** `industryManagerService.js:88` -> `industryRuntimeState.js:4774` -> `industryInstallSettlementState.js:207` -> `industryInstallItemCustody.js` -> `itemCustody.transfer`. Four layers; the bottom two are shared with reprocessing and PI.
15. **PI colony -> customs office -> item store.** `planetMgrService.js:1346 UserLaunchCommodities` moves goods out of a colony through `planetaryCustomsItemCustody` into a hangar. PI's *simulation* (`planetRuntimeStore.js:2424`) is self-contained and needs nothing but a clock — it is the **only subsystem here that can be built with no store work at all**, up to the point goods leave the planet.
16. **PI -> structures, only for skyhooks.** Classic customs offices are `planetOrbitalState`, independent of Upwell. Skyhooks (`skyhookOfficeReplacement.js`) need structures. Build classic COs first.

**Recommended order:** store move/transfer + change notification (shared, blocking) -> reprocessing at NPC stations -> industry manufacturing at NPC stations -> PI colony sim + classic customs -> mining (after fitting and Destiny land) -> compression -> structures variants of all four -> POS/moon mining never.

## Notes for the coordinator

**The brief's premise on our store needs one correction.** `Item` in `item.rs:361-373` *does* carry `location_id` and `flag_id`, and `used_volume` (`:473`) already keys on the pair — they are there because the client's item row needs them. What is absent is any **operation that changes them**: `Store` exposes `insert` (`:490`) and `spawn` (`:499`) and nothing else. So the decision is not "add location semantics" but "design the mutation API", which is a narrower and more tractable question.

**Make the mutation API decision before the round starts, and make it in one file.** Four lanes will each need: move an item, transfer ownership, split a stack, merge a stack, consume a stack, and tell the client. If that lands four times it will not merge. The minimum shared surface, from their model: `(owner_id, location_id, flag_id)` as the only address; a staged edit list applied all-or-nothing; a returned `changes` vector of `(item, previous)` pairs for the notification; one centrally-allocated synthetic location range for escrow. That is the whole decision and it is maybe 400 lines.

**Do not port the idempotency receipt ledger unless we persist items.** Their entire receipt apparatus (`itemStore.js:86`, `:5461-5640`, `_shared/settlementSequenceWatermark.js`) exists because they have no transactions and an in-memory snapshot that can run ahead of SQLite (`itemStore.js:264-267`). If our items die with the process, a staged-edit plan gives us atomicity for free and the receipts buy nothing. If we do persist, read `invBroker/ownerTransferIdempotencyKey.js:11-23` — 38 lines, almost all comment, and the single best-reasoned piece of code in the tree.

**Two surprises worth knowing.**
1. **Mining does not use their own custody boundary.** `miningRuntime.js:992` mints ore with a direct `itemStore` call, *then* decrements the asteroid at `:1018`. Compression (`inSpaceCompressionMgrService.js:62`) and the industry chat commands (`industryChatCommands.js:22`) also bypass it. The custody machinery covers industry install, reprocessing, PI customs, market, contracts, missions — but not the thing the brief assumed it covered. Their implicit rule is "custody for moving existing goods across an ownership boundary; direct writes for mints", and it leaves mining with a real duplication window.
2. **The asteroid-ore distribution table is only obtainable from a client.** `database-creator.js:3180-3185` emits an **empty** `asteroidTypesBySolarSystemID` with the note "Generated without client private asteroid map", and the populated version (3,974 systems, 24,071 assignments) comes from `res:/staticdata/asteroidtypesbysolarsystemid.pickle`. This is the strongest possible vindication of our read-the-client model: they had to do the same thing, and their SDE path simply cannot produce it.

**Biggest unknowns, in order.**
- Does 3619879's `typematerials` expose `relativeProbability`? Their build does not (`database-creator.js:2516-2518`), so they silently use uniform 1/n for 10 ore types. If ours does, their reprocessing code is wrong for us. **Cheapest high-value check available.**
- Does 3619879 ship `blueprints` in client FSD? If not, we need a plan for blueprint data that is not "ship the SDE".
- What is the `UserUpdateNetwork` payload shape on 3619879? Their 13-opcode enum (`planetCostCalculator.js:24-37`) is the only documentation that exists.
- Is `planetResources` client-readable, or server-authoritative? Flagged as a guess above.

**What to look at next, if you want more depth.** `services/inventory/invBrokerService.js` is **14,253 lines** and is the drag-and-drop broker every client inventory action goes through — it is outside my assignment but it is the largest single file in the inventory tree and it is what actually calls custody from the UI. If the store-mutation design is the shared decision, somebody should read `invBroker/fittingOperations.js` (1,696) and `invBroker/packaging.js` (319) before it is finalised. Also unexamined by me: `services/starbase/` (POS bodies), `space/asteroids/` (3 files — where belt rocks actually come from), and `_shared/averageMarketPrices.js` (the pricing seam industry depends on).

**Finally: zero tests, confirmed for this area and the whole repo.** `find` over the repo for `*.test.js`, `*.spec.js` and `test/` directories returns nothing. Every "functional" above means "the code path is complete and internally consistent on reading", never "verified". Their substitute is chat commands — `industryChatCommands.js` (778 lines) and `reprocessingChatCommands.js` (405) exist largely so a developer can drive the pipeline by hand. If we port a formula, we should port it with a test; we would be the first.
